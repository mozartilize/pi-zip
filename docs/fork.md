# Fork features

This fork tracks upstream pi-zip. Upstream documentation describes the base behavior; this document describes the fork's overrides and additions. See [UPSTREAM.md](../UPSTREAM.md) for the module boundaries and update procedure.

## Summary formats

Only v2 and v3 are emitted. V3 is the default; `PI_ZIP_SUMMARY_V2=1` selects v2. Existing upstream, fork-v1, v2, v3 and native Pi summaries remain readable for migration. `src/summary-engine.ts` dispatches v2/v3 and extends the parser, while importing shared parsing, budgeting, serialization and provider-call logic from `src/summary.ts`. The runtime is `ZipFork` in `src/run-fork.ts`, which inherits the lifecycle and producer from upstream's `Zip` in `src/run.ts`.

### Format v2: verbatim requests and the request floor

`PI_ZIP_SUMMARY_V2=1` switches the summary from the default format v3 to format v2, which keeps user requests verbatim by default, numbered from the raw ancestor branch (`R<n>`). Ordinary rows show only the request number and handle, without a redundant `verbatim` qualifier; older rows with that qualifier still parse. Apart from the skill-envelope exception below, requests are shortened only under a real overflow. `summaryTokensPlanned` is a soft target: a summary may grow past it up to the hard room before requests are touched, so the soft target is never a licence to lose text.

Request text is compressed in two deterministic steps, and only after everything else is gone (unpinned evidence, all evidence, commitments, then the intent quotes that repeat verbatim requests, then old prose, the newest prose, and the state):

- **E1, excerpts.** Every request keeps its row and handle. The text budget is water-filled across requests: short ones stay whole, while long ones keep at least 200 content characters in total, split between head (2/3) and tail (1/3). The complete rendered row, including its qualifier and quote prefixes, must be shorter than the original row; otherwise the original stays. An empty active state does not prevent validated intent or the newest prose from being retained when they fit.
- **E2, archived ranges.** When the floors do not fit, eligible old epochs are archived oldest-first. Only requests with branch-verified identities may be newly archived; legacy or unverified text stays resident. Consecutive numbers become compact ranges (`R1–R15 archived, not resident`); gaps are not filled. The newest epoch that holds requests stays resident, so E2 cannot rescue every overflow, including a single oversized epoch. Recall uses `zip_recall({ requests: "1-15" })`, or `requests.txt` in file-only mode. At the next compaction, available raw requests are restored; missing spans remain compact ranges with their full count and bounds, even above 512 requests. Invalid, reversed, unsafe-integer or count-mismatched ranges are rejected without expansion.

Evidence, commitments and old prose do not come back in either step; omission counts and source handles remain for recall where the source is available. If the smallest permitted representation still exceeds the room, the cut fails with `request-budget-overflow` and is not adopted. Telemetry reports required and available sizes plus a section breakdown. Archived requests are counted as archived, not as empty verbatim rows, even when the raw branch is unavailable.

One deliberate exception sits outside both steps: a Pi `<skill>` expansion is resident-view compression, not user wording. The summary's request rows keep `/skill:name` plus any text the user typed after it (recallable and re-expandable, and counted as `skill references`, never as verbatim), and `originalRequestChars` measures the available prepared text before that compression (it cannot reconstruct unknown lengths from an archive without the raw branch). The narrative call, however, reads the expansion as the user had it: constraints a skill carries are exactly what the durable prose and the state have to keep.

### Format v3: a state digest

Format v3 is the default summary format (`PI_ZIP_SUMMARY_V2=1` selects format v2 instead). Format v2 appends one epoch per compaction and keeps every request verbatim, so it grows with the session. Format v3 keeps a bounded state instead:

- **Digest.** Five sections of numbered items (`- [i12] …`): architecture, settled decisions, discarded approaches (tried or rejected, with the reason), test health (baseline failures versus new regressions) and open work. One narrative call reads the previous digest, the previous intent quotes and the new slice, and replies with operations only: `ADD iN:`, `EDIT iN:`, `MOVE iN:` (to the section it is written under) and `DROP iN: reason`. The code carries every item that no operation names word for word, so an item the model forgets is not lost. A drop without a reason, or an operation on an item that does not exist, changes nothing. Item numbers are stable across compactions and are written `iN` because sessions are full of `#N` issue and task numbers. A section over its size (`decisions` 6,000 characters, the others 2,000, tests 800) is marked OVER BUDGET in the prompt, which asks the model to merge items; the code drops nothing for size until the hard room. A failed call, or a reply without section markers, keeps the whole previous digest and marks it `possibly stale`. There are no tier merges. Diagnostics list every dropped item with its reason.
- **Room.** The summary is filled up to the plan's target, at most 8,000 tokens (`PI_ZIP_SUM_V3_TARGET`). The ceiling is fixed because the plan's target is at least the previous summary's size, so filling to it would never let the summary shrink.
- **Requests.** Requests keep their raw-branch numbers. At least the newest 8 substantive requests stay verbatim (`PI_ZIP_SUM_V3_RECENT_REQUESTS`). Older requests come back newest first while they fit in half of the free room, and again after the evidence if room is left. The window is contiguous: a long request that does not fit stops it. Older requests become `digested` ranges, but only when the raw branch can return their exact text (number and handle match); otherwise they stay resident. The call also lists the source labels of requests in its slice whose whole content is assent or a go-ahead to continue. The model judges this by meaning, in any language; code has no keyword or regex fallback and only checks that each label is a user request of the slice. Such requests become `go-ahead only` ranges. A request over 200 characters is never folded, which bounds the cost of a wrong judgement. Every range stays recallable with `zip_recall({ requests: "M-N" })`.
- **Intent.** Quotes must be exact NFC spans of a request of the slice or of a request that a previous intent quotes. They are checked against the raw branch, so a digested request can still supply them. A request judged go-ahead only is no source: assent alone states no intent, and what was approved belongs in an open-work item. Each quote may name the digest item it is about (`- R183 · source … · about i37`); the item gives its scope in the assistant's words, the quote stays the user's. A link to an item that no longer exists is removed; the quote stays.
- **Evidence.** Only outputs that the model selected (exact quote, at most 20 a call, `PI_ZIP_SUM_V3_SELECT_EVIDENCE`) or that the digest names by handle or execution id are listed. No rule guesses which other output holds a conclusion; status polls, task-list updates and routine reads stay recallable only. This slice's records and the named ones are always listed; selected records carried from earlier summaries fill the free room after the first share of requests, newest first. Any output left out is still recallable by grep without a handle.
- **Hard room.** Above the hard room, in this order: evidence, then the oldest resident requests that the branch can return, then the intent quotes, then whole digest sections (omitted), then request excerpts. If it still does not fit, the kept part of the view alone fills the room, which no summary size can fix: the minimal summary is still used (it always shrinks the view), and diagnostics record `overRoom`. Unlike format v2, format v3 never fails a cut with `request-budget-overflow`: every request it leaves out stays recallable.

A previous v2 summary migrates on the first v3 compaction: its request rows and archived ranges keep their numbers, its selected evidence carries, and its epoch prose (head and tail, at most 12,000 characters) and state are split into numbered decision and open-work items at list markers and paragraphs. The call can then move, edit, merge or drop them. Older formats and Pi's own summaries migrate the same way through their narrative. Readers of older formats see the resident requests, the digested count and the digest as one epoch.


## Folding, pressure and recovery

- Folding retains the upstream 40K working target. Summary preparation and application have separate pressure gates: preparation begins at `min(80% of safe room, 140,339.2)`, application at `min(80% of safe room, 400,000)`. An unknown window does not authorize a summary unless `PI_ZIP_SUMMARY_AT` overrides the threshold.
- A smaller-window model switch first tries folds, then an existing checkpoint, then a new summary. Rescue may fold protected outputs or cut up to the current request; originals remain recallable. If the current request still cannot fit, the run stops without deleting history.
- A repaired length-stop boundary may use its summary immediately and continue once per user turn.
- Placeholders include a UTC fold timestamp derived from the newest message in their planned view. Persisted placeholders are never re-rendered.
- Summary command directories use stable aliases (`[a] make`); exact slice/truncation checks determine whether a read still matches disk.

See [fork-design.md](fork-design.md) for the decision rules and limits. The optional judge can reorder accepted folds but cannot relax the planner's eligibility or price law.

## Extended recall

```ts
zip_recall({ requests: "20-41" })
zip_recall({ grep: "chọn cách 2", scope: "all" })
zip_recall({ grep: "decision", scope: "assistant" })
```

Requests use 1-based raw ancestor-branch numbering. Assistant recall exposes visible text only, not private reasoning. With no arguments, `zip_recall` waits for the current request's pending retrieval findings. In file-only mode, `requests.txt` supplies the request ledger. A failed or unanswered recall does not mark an output as recalled.

## Ledger

Every decision is also written as one JSON line per event, in a file per Pi session: `~/.pi/agent/pi-zip/logs/<session>.log` (`PI_ZIP_CACHE_STATS` and `PI_CODING_AGENT_DIR` move it like the learned cache data). This is the only place a failure that never reaches the terminal shows up: the `error` of a `judge` record (a refused call, a reply that does not parse), a `summary` call that failed, a fold that refused, an edit another extension made. A parsed `judge` record also lists `verdicts`: per output its handle, tool, answer triple (`f`, active/finished/lookup, `-` when the reply had no valid line), resulting verdict and folded state, so a later fold can be traced to the facts behind it. Nothing reads it back; pi-zip never depends on it.

The folding trace has three stages:

- `judge_skip`: why no call was started (`pending`, `below-pressure`, `batch-too-small`, `cadence`, `failure-limit`, or insufficient candidates). It includes request count and eligible handles where available. Repeated identical skips are suppressed.
- `judge`: each `verdicts` row has `applied`, so a parsed answer can be distinguished from a verdict stored for planning. `streamChars`, `partial`, `applied` (count), `cancelReason`, and `resultDisposition` show what survived an interruption. `partial-applied` means some received rows were retained; `stale` means they were logged but not applied.
- `law.foldDecision`: per output, handle `h`, request-age, current verdict (`unscored` if none), eligibility `group` (`0`: older turns, `1`: pause-readable, `2`: aged protected-turn output; `null`: ineligible), `planned` (proposed by an application plan), and `selected` (accepted for application). Its overall reason distinguishes `guard-rejected`, `back-to-back`, `no-plan`, and `selected`. The existing `law.steps` explain the cache cost; the later `fold` record confirms persistence. Trigger names `cold` and `valve` describe cache probability, not who classified an output.

Judge calls consume text stream events when available. On settle/run end they retain complete newline-terminated fact rows before aborting. Timeout, error, and length stops can retain such rows too. Missing, malformed, duplicate, and unfinished rows do not replace existing verdicts; fixed rule-based verdicts remain protected. Scope/dependency changes, session/model changes, shutdown, and disabling pi-zip invalidate the snapshot instead. The provider is still cancelled; this does not wait for the remainder of its response.

- `PI_ZIP_LEDGER=/path/to/file` writes that file instead, and `PI_ZIP_LEDGER=off` (or `0`) writes nothing.
- A session file that grew past 8 MB is rotated at the next session start: the old one stays as `<name>.1`.

## Lookup cue

When a new request names an earlier output by its handle, or by the same full path or URL that a call used, its first request ends with one short note. The note names at most three of those outputs and asks the model to recall them with `zip_recall` instead of repeating the call. The match is exact and needs no model call. Outputs that a compaction took out of the view count too. An output shown in full, or a path whose newest call was an `edit` or `write`, gets no note. The note is not saved in the session. Each note writes a `lookup_hint` ledger record. `PI_ZIP_LOOKUP=0` turns it off.

## Session memory

pi-zip keeps a derived SQLite database of the open session next to its file (`<session>.memory.sqlite`; `PI_ZIP_MEMORY_DIR` moves it), and at a new user prompt it asks a retrieval model what earlier work is worth bringing back.

**Nothing is injected while the model still sees every output.** Retrieval starts only once earlier output is out of the model's view: a folded tool output, or a compaction. Until then the database is filled and no model is called.

**Storage is deterministic.** The database holds a row per session entry, one segment per request or per model step (a tool call and its result always share a segment), a small graph (call -> result, request -> step, file/URL/command references) and an FTS5 index over every user, assistant, thinking, tool-call and tool-result text block. No model decides what is stored, and the judge is not involved. The session file stays the source of truth and is only read.

**Only the open session is indexed**, in full the first time and then only new entries after each turn; other sessions are untouched until they are opened. A changed source entry rebuilds that one database. Large initial backfills project at most 500 entries per tick. Each queued tick belongs to a ledger generation; leaving the session or closing the ledger cancels and invalidates it. A failed batch rolls back and sets `error`, not `ready`. A later retry reconciles the committed prefix and resumes in bounded batches; three failed attempts stop retries until the session is reopened. Only catching up with the current source sets `ready` and clears the error. Retrieval searches the active branch only.

**Retrieval, on read only.** Every hidden text block of the active branch can be found: earlier user requests, assistant text (completed final answers are labelled conclusions; other assistant text is mid-turn text), reasoning (labelled unverified), tool calls and tool outputs. Searchable are the entries of the active branch before the latest compaction record, including the part the compaction kept in view (the note is advisory, and the model may have lost track of retained text too), plus outputs folded by pi-zip. Branch order defines "before", not timestamps. An absent entry alone is not proof of hiding. Entries whose handle the prompt names are resolved directly and kept first, each on its own.

**Planner call (in the background).** At a new prompt a first, tool-less model call reads the request (without `<skill>` blocks; a request over 4000 characters as its first 1000 and last 3000) and a bounded tail of the model view: user and assistant text of the last 3 user turns, each tool call as one line, no tool output bodies, at most 2,000 words (oldest dropped); right after a compaction, when that conversation is under 300 words, the first 500 words of the compaction summary are added. It decides only whether the request is a bare continuation or acknowledgement (then nothing is searched); it does not judge whether the visible context already suffices. Otherwise it splits the request into its distinct sub-questions (aspects) and writes keyword queries for each of them along four facets (what, why, how, when) in every language of the request and the visible context, with identifiers, paths and error codes verbatim (at most 16 queries). It runs at the lowest thinking level the model supports. A failed or invalid plan falls back to the request's own words (every distinct word up to 128; a longer request gives its first 32 and last 96). The main model does not wait for this call: while it is in flight, the request's own words are searched locally (milliseconds), and the main model waits only for that search. If it has candidates the pending note is shown from the first request. The planner's keyword search then replaces it; a failed plan uses the own-words result. The record keeps both (`early` for the own-words search) so they can be compared.

**Search.** One FTS5 search per keyword query (its words, plus each multi-word keyword as a phrase), matched in text and identifiers, not in kind labels. The searches are merged round-robin in two levels: within one aspect, the first entry of each of its queries, then the second of each, and so on (its "why" query first, since requirements and decisions are why a question about behavior is asked); then across aspects, so every sub-question of the request gets its own candidate slots instead of one verbose aspect taking them all. File paths and code symbols in the prompt also traverse the referential graph to hidden tool outputs, as one more merged list. A matched tool call brings its hidden result (one hop over the call -> result edge) right after it.

**Candidates.** The default cap is `min(32, ceil(8 × sqrt(T)))`, where `T` is the number of distinct topics (aspects) in valid keyword searches, at least 1. Thus 1/2/3/4 topics get 8/12/14/16 candidates; more facets or languages for the same topic and the graph stream do not increase the cap. This sublinear growth is a cost/coverage heuristic, not a measured optimum. An unplanned search counts as one topic. Candidates keep their merged order; explicitly handle-named entries come first and are additional to this cap. Separate executions keep their own handles, timestamps and whole-output outcomes even when their excerpts are identical; only repeated passages within the same entry are deduplicated. Conclusions are titled by the request they answered and quoted from their winning passage (up to 1500 characters); tool outputs keep a bounded issuing-call title (up to 160 argument characters) when the call belongs to searchable history, even if retained in view, so the helper can distinguish source components. Calls outside search scope stay plain; an entry may merge up to 3 matching chunk passages. Up to two hidden thinking excerpts from the same step may be attached as unverified context.

**Bounded graph lookup.** At most 6 distinct paths and 6 distinct code symbols are queried per prompt, with explicit inline references and the end of the request outside fenced code preferred over pasted code. Traversal stops when its 30-chunk pool is full. Symbols may match the output body or identifiers without occurring in the call title. Both path separators are accepted, including Windows keys in existing databases; no rebuild is needed. FTS keeps at most 3 chunks per entry before its row limit, and carries only IDs and scores through the ranking sort before fetching the selected text.

**Input packing.** The answer call gets at most 48,000 characters of quoted evidence (source headers, passages and optional thinking). This budget is separate from its instructions, the bounded 4,000-character request view and at most 1,800 characters of recent context; **total input can exceed 48,000 characters**. Packing first admits one complete passage per source, then extra passages in rounds, then thinking. A passage that does not fit is skipped, not a reason to stop considering later sources. Exactly identical passage text is quoted once with all its source IDs. Each execution still has its own handle, timestamp, outcome and independent need/citation decision; sharing text never grants need to another source. The candidate pool/ranking is unchanged. See [packing measurements](retrieval-packing.md) for the input-size trade-off.

**Time.** Every evidence item carries when it was recorded and how long before the request; the model is told that a later conclusion, the recent context or the request supersedes it, and that a question about the current state is not answered by an older item. Each handle in the note shows its age, and statuses read `earlier conclusion`, `earlier user request` (only user requests cited), `seen in output` (a named tool output showed it then) or `uncertain`. The status follows what a finding cites; the model can lower it to `uncertain` but not raise it. A named tool result also carries the outcome of its whole output (`exit 1, 21 passed, 1 failed`), since the excerpt alone may miss it.

**The answer call selects and summarizes.** Like the fold judge, the model evaluates each item independently: the new request must depend on what the item concluded (a decision, a result, an explanation), not just share keywords or a file. To keep the reply short it lists only the needed items, each with the dependency as its reason; an unlisted item is not needed. Only listed items can supply findings or recall suggestions. A listed item without a reason, listed twice, or listed with a need other than `Y` is excluded. The log still records a decision for every item (`Y`, `N` for not listed, `U` for an invalid listing). A finding with any rejected citation is dropped in full. Recent context is used to judge need, not as a summary source. Thinking is unverified supporting context, not a result. No eligible candidates means no call. A search with fewer full-text rows than `PI_ZIP_RETRIEVAL_MIN_HITS` (default 11; 0 turns it off) skips the call too (`stage: "weak search"`; every record that reaches this check carries `gate`: `minHits`, `hits`, `named`, `maxMatched`, `skipped`), unless the prompt names a handle: in the recorded logs, 26 searches had at most 10 rows and the answer call kept nothing for 21 of them. No needed items means no note.

**The answer call runs in the background.** When the search found candidates, the main model starts at once and its requests carry a pending note right after the prompt: a historical retrieval is running, its findings come in a later message, and `zip_recall` with no arguments waits for them. When the findings are ready they are appended at the end of the next request of the run (never inserted earlier, which would change what was already sent), or placed right after the prompt if they were ready before the first request; when nothing relevant was found and the pending note was shown, a one-line "nothing relevant" note closes it. Findings returned by `zip_recall` are not repeated. Later requests repeat each note in the same place, so the run keeps one cacheable prefix. The answer call has its own hard timeout (20 seconds by default). When a run ends before any request showed its findings, they are kept for the next prompt. If the answer call is still running, it is allowed to finish first (`memory_carried`, `ready` false). They join the next prompt's note when that prompt is a continuation or its searches found a handle they cite. They are put after its own findings, under a line saying they were prepared for the previous request. Otherwise they are dropped (`memory_dropped`, `next request unrelated`). New prompts, session changes, branch changes, compaction, and disabling pi-zip (`/zip off`) cancel pending retrieval; `/zip off` stops retrieval calls entirely while deterministic indexing continues. Notes are never written to the session file. Errors skip retrieval without changing folding or compaction.

The note carries one line per finding with the handles it came from, plus folded outputs worth reopening with `zip_recall`. It runs on the same model as the judge: `PI_ZIP_JUDGE_MODEL=provider/id`, optionally with `:level`, which then also sets the thinking level of these calls. Without that setting it takes the lowest input-price model on the current provider with a 32K window. `PI_ZIP_RETRIEVAL_TIMEOUT_MS` sets the timeout of each call (default 20000). `/zip-memory` shows the open session's ledger status.

The log is made to be traced and tuned later. One JSON line per event: `memory_config` (the knobs this session runs with), `memory_backfill` (reconcile, entries, ms, done), `memory_ingest` (entries added), `memory_retrieval` (one per prompt, joined by `requestId`), `memory_inject` (`kind`: pending or final), `memory_wait` (a `zip_recall` with no arguments waited for the findings), `memory_usage` (at run end, for a run whose request carried a note: which cited handles the model recalled with `zip_recall` or named in its own text, and `reused`: the note's distinctive finding terms (backticked spans, paths, identifiers, numbers; `terms` counts them) that an assistant message repeated after delivery, excluding terms already present in the prompt or model view at delivery, or shown by a tool result first; `used` is true for a recall or a reused term, `usedBy` says which; naming a handle alone does not count, since it may mean disputing it), `memory_carried` (a run ended before its findings were shown; they wait for the next prompt), `memory_dropped` (the findings never reached the model: the answer did not finish, or the next prompt was unrelated or had no retrieval) and `error`. A `memory_retrieval` record carries `stage` (where a skipped run stopped, or `prepared`; actual insertion emits `memory_inject`), `latency` per step (early, plan, search, foreground, answer), `early` (the own-words search: hits, candidates, handles), `carried` (the request whose late findings joined this note), `queries` (the planner's keyword queries, or `terms` when it failed), `calls` (model, level, ms, tokens, cost, stop reason, reply length), `input` sizes (`inputChars` for the full user message, `evidenceChars` for the serialized quoted evidence including source headers), `sentRefs`, physical `passages` and `sharedPassages` inside `input`, `terms`, `hits`/`inBranch`/`candidates`, `drops` (what validation removed and why) and an `evidence` table with the hiding reason, attached thinking count, and citation use (`cited`). `decisions` records each item's `need` and reason, including when all items are rejected. `drops.notNeeded` counts rejected citations. The evidence table is retained even when no note is produced. Trace is on by default during tuning; `PI_ZIP_MEMORY_TRACE=0` disables raw reply logging. `calls[].reply` includes up to 4000 characters of returned text even when the response ends with `length` or an error. `thinkingChars` records the size of any returned thinking, not its contents. Raw replies can contain session data. With trace on, `memory_retrieval.note` holds the exact note text.

`npm run index <session.jsonl>... [-- --out <dir>]` builds or updates the same database for any session file outside Pi, reading the session file only and printing one JSON line of counts per file. `bun bench/memory-bench.ts` measures indexing and summarises retrieval from the logs.

## Optional background judge

  Set `PI_ZIP_JUDGE=1` to enable a background model that ranks tool outputs. It is off by default. The planner still decides what may be folded. The judge only changes the order inside that set.

  - `PI_ZIP_JUDGE_MODEL=provider/id` selects an available model. Add `:level` (`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`) to request a thinking level, for example `github-copilot/gpt-6-luna:low`; an id that itself ends in such a suffix matches whole first. The level is sent only when the model advertises it. With no capability metadata, the request sends no thinking level and Pi keeps the provider default. With no explicit level, no level is sent either, except to a model whose provider picks the effort when none is named: GitHub Copilot models on the Responses API, and models whose thinking-level map has `off: null`. Such a model gets its lowest supported level above `off`. At Copilot's default effort, a 13K-token `gpt-6-luna` judge call took 34-43 s and hit the 30 s timeout; at `low` it took 7-9 s. Otherwise, pi-zip chooses the lowest input-price model on the current provider with at least a 32K context window. If none is available, the judge stays off for that session.
  - `PI_ZIP_JUDGE_MAX_TOKENS=16384` caps the judge output, thinking included. The cap also stays within the model output limit and the context room left after the input. Each `judge` ledger record logs `maxTokens`, `stopReason`, `outputTokens` and `reasoningTokens` for tuning. It also logs why the call ran: `reqCount`, `superseded`, `eligible`, `foldedHit` and `scopeChanged`. It logs the input size: `known`, `folded`, `evidence` and `inputTokens`. A parsed reply adds `diag`: code-derived C/H/N/U counts, malformed, foreign, missing, duplicate and bad-evidence lines, `facts` (the histogram of accepted answer triples, counted after the malformed, foreign, missing and duplicate guards, so a decisive `NNN` row is distinguishable from a row where the context left a fact unknown; lookup validation runs later, so an uncited `N` keeps its fact), and up to 10 lookup decisions with their outcome (`need`, `live`, `uncited`). The code selects matching references; the model does not return citations. A reply that does not parse keeps its first 300 characters as `replyHead`. A `judge_hint` record shows each distinct hint outcome: a note sent (`shown`, `skipped`), a note dropped for lack of room, or valid N handles that were blocked as `old`, `notFolded`, `recalled`, `hinted` or `uncited`.
  - `PI_ZIP_JUDGE_AGE=10` is an additional minimum age before a live output is scored. The output must also pass the planner's fold eligibility and placeholder-saving checks. With the default protected-turn rule, that means age 60, not 10. `PI_ZIP_INTURN_AGE=0` still disables age-based folding.
  - The model reports three independent facts: `<handle> <active> <finished> <lookup>`. Each answer is `Y/N/U`. `N` means false or not applicable. `U` means the supplied context cannot establish the answer. No citations, confidence scores or priorities are requested. `active` and `finished` can both be `Y`: a finished step can still supply information needed by current work.
  - Code decides priority. `lookup=Y` with a matching user/assistant handle or full path/URL becomes need if folded, or hot if live. Otherwise `active=Y` makes the output hot, even if `finished=Y` or a lookup reference fails validation. An output becomes cold only for `N Y N`. Other combinations stay warm. Age, silence, unrelated passing checks, complementary read ranges and mere same-path calls do not establish `finished=Y`. Labels never change rent, summary production or cache prices.
  - Code, not the model, labels a superseded output cold: the same tool ran again with the same arguments, or a successful `edit` or `write` changed the file at the output's full path. A failed later call supersedes nothing. A read of another range of the same file is not a repeat. Superseded outputs are labelled at every boundary, below the pressure and cadence gates, and are never submitted. A model reply cannot replace this label. The `judge` ledger record counts them as `superseded`.
  - Recent work reserves up to 35% of the 24,000-character evidence window for recent user prompts and assistant milestone replies, then fills the remaining budget with the newest assistant tool-call steps (visible prose and one `call <tool> <args>` line per tool call ahead of thinking) and deduplicated tool-result digests (up to 560 characters with outcome hints, key lines, and head+tail preserved; older identical head+tail tool outputs collapse to a short repeat line). Signatures, ids and other provider fields are left out. The canonical 24,000-character `workReferences` window for `lookup` verification remains unchanged.
  - Current state gives each output's age, live/folded status, and local causal trace (`turn=t/T`, caller intent `why=...`, same-turn edits `turnEdits=...`, and closing milestone `closed=t_c/T (...)` or `closed=open`). Catalogue rows stay immutable so the prefix caches across runs.
  - Only new, invalidated or expired candidates are submitted. Unsubmitted verdicts keep their original expiry. The ledger records `protocol: facts-v1`, `reused` and `addedTokens`. Recent work remains available as evidence even when its output is not a classification candidate.
  - A valid `N` can add one short lookup note to a request that is already going out, naming at most three handles. It does not restore the original, start a run, or send a steer. The note requires `zip_recall`. Each handle is noted at most once per session.

  The judge receives the task prompt, candidate labels and key lines, plus bounded recent work. Recall calls and earlier lookup notes are not evidence. Choosing a different provider explicitly sends this data to that provider. Calls use Pi's existing model credentials and can consume quota or incur charges. Only one judge call runs at a time. Errors retain still-valid verdicts. Verdicts expire after 20 requests. A changed user request invalidates the previous scope. New explicit references and live/folded transitions invalidate affected verdicts before the boundary's planner reads them. Invalidated in-flight results cannot restore old advice. Two consecutive provider/parse failures stop calls for the current run.

  This remains a chat judge, not an independent-logit System One classifier. The current transport uses validated Y/N/U fact lines. Provider-enforced JSON schemas are not enabled because enforcement through the configured endpoint is not verified. There is no corrective second call or generated confidence score. See [judge replay](judge-replay.md) for offline measurement. Tests of the parser and policy do not establish model accuracy.

  `/zip` adds judge call cost, partly-unknown-verdict and error counts for this process. A verdict counts as unknown when at least one of its three facts came back U, so the count is taken from the reply: it can overlap the cold, hot and need counts, and it includes handles a fixed verdict kept. Records written before `diag.facts` existed used the narrower policy-code-U count. Judge verdicts and counters do not survive a restart. Hint dedup is stored in the session and is not sent to the model.
